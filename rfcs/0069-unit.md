## Summary

Add an optional `unit` field to `schema[].properties[]`. It is not required and empty by default. It states the unit of measure of the values in a property, for example `kg`, `t`, `kWh`, `ISK`, `%` or `persons`.

The standard recommends a **default unit list** based on the **SI units** and the **UCUM** unit codes. Tools offer it for search and selection. If a unit is not in the list, the author types it as **free text**.

## Motivation

### A number without a unit is not usable data

A data contract can say that `value` is a `number` with `precision: 12, scale: 2`. It cannot say whether `value` is in **kilograms or tonnes**, **ISK or EUR**, or **percent or persons**. The type tells a consumer how to *store* a value. The unit tells them what it *means*.

### Data from many sources has to be calculated together

The real problem shows up downstream, in the data warehouse.

A statistical office, like many large organisations, collects data from many different sources: surveys, administrative registers, company reports, other agencies, sensors. Each source has its own conventions. In the warehouse, these collections are **combined and calculated with**:

- Totals are summed across sources (fish catch from logbooks + landings from harbour registers).
- Rates are computed from two collections (energy use ÷ population, emissions ÷ GDP).
- Time series are joined across a change of source or method.
- Values are compared between regions, sectors or countries.

Every one of these operations is only correct if the units are compatible. If they are not, the result is wrong **without any error message**:

| Source A | Source B | What goes wrong |
|---|---|---|
| Catch in `t` | Catch in `kg` | Sum is off by a factor of 1 000 |
| Energy in `GWh` | Energy in `TJ` | Sum is off by a factor of about 3.6 |
| Turnover in `ISK` | Turnover in `thousand ISK` | Sum is off by a factor of 1 000 |
| Share in `%` | Share as ratio (0–1) | Comparison is off by a factor of 100 |

Today, the unit is usually hidden in a column name (`weight_kg`), a description, separate documentation or someone's head. None of these travel reliably with the data, and none can be checked by tools.

The data contract is the place where producer and consumer agree on what the data means. The unit is part of that agreement.

### Use cases

1. **Correct calculations in the warehouse.** Engineers and analysts can see, before they combine two columns, whether the units match or a conversion is needed.
2. **Checks in pipelines.** A pipeline or AI agent can refuse to add two columns with different units, or flag it.
3. **Change detection.** A change of unit (`kg` → `t`) without a version bump can be flagged as a breaking change, even though the physical type stays the same.
4. **Consistent metadata catalogue.** The metadata catalogue reads `unit` directly from the data contract when it imports a contract. This keeps the unit shown to users in the catalogue the same as the unit agreed in the contract. Without a standard field, units are copied into the catalogue by hand, and the catalogue and the data drift apart over time.
5. **Meaningful quality rules.** Range checks (`minimum`, `maximum`) only make sense when the unit is known.
6. **Beyond statistics.** Energy, IoT, finance (currency), healthcare (lab values) and logistics (weight, volume) have the same need.

### Why defaults plus free text

- **Defaults give consistency.** Without a shared list, the same unit gets written as `kg`, `KG`, `kilo` and `kilograms`, and tools cannot tell those are the same. SI and UCUM are international standards that most domains already use, so they make a neutral common base.
- **Free text gives coverage.** No list holds every unit. Statistical units such as persons, households or index points, and domain-specific ones, must still be possible.
- **The field stays simple.** It is a single string, so it is easy to adopt and easy to extend later with organisation-specific lists (see the related Entropy Data proposal) without breaking anything.

## Design and examples

### Specification

| Key | UX label | Type | Required | Default | Description |
|---|---|---|---|---|---|
| `unit` | Unit | string | No | empty | Unit of measure of the values in this property. Use a code from the default unit list where possible, for example `kg`, `kW.h`, `ISK`, `%`. Otherwise use free text, for example `persons`. |

### Default unit list

The default list has four parts:

1. **SI base units** (from the International System of Units, published by BIPM).
2. **SI derived units and prefixes** (kilo-, mega-, giga-, milli-, and so on).
3. **Non-SI units accepted for use with SI**, such as tonne, litre, hour, day and hectare.
4. **Common dimensionless units and currencies**: percent, per mille, and ISO 4217 currency codes.

Codes are written as **UCUM** (Unified Code for Units of Measure) codes. UCUM is machine-readable and covers all SI units and prefixes. Every UCUM unit is also valid in UCUM-aware tools, so the default list can be extended beyond this table.

| Measurement type | Unit | Code |
|---|---|---|
| Length | metre, kilometre, millimetre | `m`, `km`, `mm` |
| Mass | kilogram, gram, tonne | `kg`, `g`, `t` |
| Time | second, minute, hour, day, week, month, year | `s`, `min`, `h`, `d`, `wk`, `mo`, `a` |
| Electric current | ampere | `A` |
| Temperature | kelvin, degree Celsius | `K`, `Cel` |
| Amount of substance | mole | `mol` |
| Luminous intensity | candela | `cd` |
| Area | square metre, square kilometre, hectare | `m2`, `km2`, `har` |
| Volume | cubic metre, litre | `m3`, `L` |
| Speed | metre per second, kilometre per hour | `m/s`, `km/h` |
| Energy | joule, terajoule, kilowatt hour, gigawatt hour | `J`, `TJ`, `kW.h`, `GW.h` |
| Power | watt, kilowatt, megawatt | `W`, `kW`, `MW` |
| Voltage | volt | `V` |
| Pressure | pascal, bar | `Pa`, `bar` |
| Frequency | hertz | `Hz` |
| Proportion | percent, per mille, ratio | `%`, `[ppth]`, `1` |
| Currency | ISO 4217 code | `ISK`, `EUR`, `USD`, … |

### Guidelines

- Use `unit` mainly on numeric properties. It may also be used on other types that hold quantities.
- Leave it empty when a unit does not apply (identifiers, names, codes, dates).
- **Search the default list first.** Tools should offer it as autocomplete or a drop-down list.
- **Use free text if the unit is not there**, for example `persons`, `households`, `index points`, `FTE`. Keep it short and use the same spelling across contracts.
- If values are scaled, write it in the unit, for example `thousand ISK` or `1000 t`.
- Context about the variable itself, such as an index base period (May 1988 = 100) or constant prices, goes in `description`, not in `unit`.
- Changing `unit` **should** be treated as a breaking change.

### Example 1: Combining two sources

```yaml
schema:
  - name: fish_landings
    logicalType: object
    properties:
      - name: species_code
        logicalType: string
        description: "Species code"

      - name: landed_weight
        logicalType: number
        description: "Landed catch, live weight"
        unit: t                    # from the default list

      - name: landed_value
        logicalType: number
        description: "Value of landed catch"
        unit: thousand ISK         # free text (scaled currency)

      - name: vessels
        logicalType: integer
        description: "Number of vessels landing"
        unit: vessels              # free text, not in the default list
```

A second contract from a harbour register defines `weight` with `unit: kg`. Before summing, the warehouse team can see the two sources differ by a factor of 1 000.

### Example 2: Price index and rate

```yaml
schema:
  - name: consumer_prices
    logicalType: object
    properties:
      - name: cpi
        logicalType: number
        description: "Consumer price index, base May 1988 = 100"
        unit: index points

      - name: cpi_change_12m
        logicalType: number
        description: "Change over 12 months"
        unit: "%"
```

## Alternatives

### 1. Custom properties (works today)

```yaml
      - name: landed_weight
        logicalType: number
        customProperties:
          - property: unit
            value: t
```

- ✅ No change to the standard.
- ❌ Every organisation chooses its own key (`unit`, `uom`, `unitOfMeasure`), so contracts from different producers are not comparable. This is exactly the cross-source problem the field should solve.
- ❌ Tools such as validators, catalogs and editors ignore it.
- ❌ It signals that the unit is optional decoration, but for numeric data it is core meaning.

This is the workaround we use now. It shows the need, but it does not give interoperability.

### 2. `logicalTypeOptions.unit`

- ✅ Close to other value constraints.
- ❌ `logicalTypeOptions` describes the type (length, range, format). A unit describes meaning.
- Acceptable fallback if the TSC prefers it.

### 3. Unit in `description` or in the column name (`weight_kg`)

- ❌ Not machine-readable and not checkable. It easily gets out of sync. This is the current state in most datasets.

### 4. Free text only, without defaults

- ✅ Simplest possible.
- ❌ Leads to spelling variants (`kg`, `KG`, `kilo`), so contracts are again not comparable.

### 5. A closed list (only listed units allowed)

- ✅ Fully consistent.
- ❌ Blocks real cases: no list holds every unit, especially statistical ones such as persons, households or index points.

### 6. A structured object (`unit.code`, `unit.system`, …)

- ✅ More precise and machine-actionable.
- ❌ Harder to agree on and to adopt in a first step.
- Possible as a later step. Until then, tools can load extra unit lists or ontologies and write the chosen value into this field.

*To be decided by the TSC.*

## Consequences

- **Non-breaking.** The field is optional and empty by default. Existing contracts stay valid.
- JSON Schema: add `unit` (string) to the property definition.
- Metadata catalogues that import ODCS contracts can read `unit` directly into their variable or column metadata. The contract becomes the single source of truth for units, and the catalogue stays consistent with it.
- The default unit list is published with the standard (for example as `units.json`) so that editors can offer it for search and selection.
- Tools may add optional checks, such as warning on a unit change, on numeric properties without a unit, or on free-text units (as a hint, never an error).
- Precedent: ODCS already has a `unit` on SLA properties (`slaProperties[].unit`). This RFC brings the same idea to the data itself.
