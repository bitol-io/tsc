# Open Data Mesh Standard (ODMS)

Champion: Jean-Georges Perrin.

Authors: Jean-Georges Perrin.

Slack: `#bitol-wg`.

GitHub issue: [#146](https://github.com/bitol-io/tsc/issues/146).

Applies to:
* [ ] ODCS - Open Data Contract Standard
* [ ] ODPS - Open Data Product Standard
* [ ] OORS - Open Observability Results Standard
* [ ] OOCS - Open Orchestration and Control Standard
* [ ] OMMS - Open Maturity Model Standard
* [ ] OMDS - Open Metadata Difference Standard
* [ ] OSDS - Open Semantic Definition Standard
* [x] ODMS - Open Data Mesh Standard (this RFC)

## Summary

Define an Open Data Mesh Standard (ODMS): a YAML document, `kind: DataMesh`, that declares the domains a mesh is made of, who owns each one, and which data products, contracts and policies belong to it. It composes the existing Bitol standards by reference and adds no schema, product or contract of its own.

## Motivation

`domain` is a free-text string on both an ODCS contract and an ODPS data product. That label is all the family says about the mesh today, and it is not enough:

- **There is no domain inventory.** Nothing states which domains exist, so `customer`, `Customer` and `customer-domain` are three different domains, and no artifact can be checked against a definition that does not exist.
- **Ownership has no home.** A data product carries its own `team`, but the domain that owns it has no owner anywhere, and an empty or under-served domain is invisible.
- **Nothing composes the family.** ODCS, ODPS, OORS, OOCS, OMMS, OMDS, OSDS, ODTS, OAAS and OUCS each describe one artifact. No document says which of them together form the mesh, or which policies apply to whom.

ODMS answers: *what is this mesh made of, who owns each part, and what governs it?*

| Standard | Answers | Analogy |
| -------- | ------- | ------- |
| ODCS | What does the data look like? | Blueprint |
| ODPS | What is the data product? | Bill of materials |
| OORS | What happened? | Inspection report |
| OOCS | What should happen? | Operations manual |
| OMDS | What changed? | Diff |
| OUCS | Why does this exist? | Business case |
| **ODMS** | **Who owns what, and what forms the mesh?** | **Site plan** |

Making the mesh explicit supports its four principles: domain ownership and data as a product become declared rather than assumed, the self-serve platform's capabilities are listed, and federated computational governance gains a machine-readable scope.

## Design and examples

An ODMS document reuses the Bitol resource header (`apiVersion`, `kind`, `id`, `name`, `status`) and extension blocks (`tags`, `authoritativeDefinitions`, `customProperties`). The recommended file suffix is `.odms.yaml`.

### Example 1: Minimal

```yaml
apiVersion: v0.1.0
kind: DataMesh
id: acme
status: active
domains:
  - id: customer
```

### Example 2: Structured

```yaml
apiVersion: v0.1.0
kind: DataMesh
id: acme
name: Acme data mesh
status: active
description:
  purpose: Customer and fulfillment data products, owned by their domains.
team:
  name: data-platform
domains:
  - id: customer
    name: Customer
    team:
      name: customer-data
    dataProducts:
      - id: customer-360
    contracts:
      - id: customer-360-contract
        version: 3.2.0
  - id: fulfillment
    name: Fulfillment
    team:
      name: fulfillment-data
    dataProducts:
      - id: shelf-warmers
governance:
  policies:
    - id: pii
      appliesTo: [customer]
      engine: opa
      url: https://governance.example.com/policies/pii.rego
      package: acme.pii
      query: data.acme.pii.deny
platform:
  capabilities:
    - id: catalog
      url: https://catalog.example.com
customProperties:
  - property: sponsor
    value: Head of Data
tags:
  - mesh
```

### Example 3: A policy in Open Policy Agent

Policies are written in the policy engine's own language. This adds a second policy to the mesh in Example 2, with a rule that requires a domain publishing data products to list the contracts that bind it:

```yaml
governance:
  policies:
    - id: contracts
      appliesTo: [customer]
      engine: opa
      url: https://governance.example.com/policies/customer-contracts.rego
      package: acme.customer
      query: data.acme.customer.deny
```

**customer-contracts.rego**:

```rego
package acme.customer

deny contains msg if {
  some domain in input.domains
  domain.id == "customer"
  count(domain.dataProducts) > 0
  not has_contracts(domain)
  msg := "customer domain publishes data products but lists no contract"
}

has_contracts(domain) if {
  count(domain.contracts) > 0
}
```

Evaluating the query against the document returns an empty set when every customer data product is covered by a contract, and one violation entry per uncovered domain otherwise.

### Fields

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `apiVersion` | string | yes | ODMS version. Initial version is `v0.1.0`. |
| `kind` | string | yes | Always `DataMesh`. |
| `id` | string | yes | Unique identifier of the mesh. |
| `name` | string | no | Human-readable label. |
| `status` | string | yes | Lifecycle state. Free text; see [Status](#status). |
| `description.purpose` | string | no | What the mesh is for. |
| `team.name` | string | no | Id of the team owning the mesh itself. |
| `domains` | non-empty array | yes | Domains in the mesh. See [Domains](#domains). |
| `governance` | object | no | Federated computational governance. See [Governance](#governance). |
| `platform` | object | no | Self-serve platform capabilities. See [Platform](#platform). |
| `authoritativeDefinitions` | array | no | Typed links to external sources. ODCS semantics. |
| `customProperties` | array | no | Platform-specific data. ODCS semantics. |
| `tags` | array of string | no | Free-form labels. |

### Status

`status` is free text, so organizations keep their own lifecycle. Two values have a defined meaning:

- `proposed`: the mesh is not yet in force; its domains and references may be incomplete.
- `retired`: the mesh has ended; its documents remain readable.

Any other value, e.g. `active`, is treated as in force.

### Domains

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `domains[].id` | string | yes | Unique domain key within the document, matching `[a-z0-9._-]+`. |
| `domains[].name` | string | no | Human-readable label. |
| `domains[].description.purpose` | string | no | What the domain is responsible for. |
| `domains[].team.name` | string | no | Id of the owning team. Without one, the mesh's `team.name` applies. |
| `domains[].dataProducts` | array | no | Data products this domain publishes. |
| `domains[].dataProducts[].id` | string | yes* | Id of an ODPS data product (*required within each entry). |
| `domains[].contracts` | array | no | Contracts this domain is bound by. |
| `domains[].contracts[].id` | string | yes* | Id of an ODCS contract (*required within each entry). |
| `domains[].contracts[].version` | string | no | Pinned contract version; omitted means the domain follows the contract's current version. |

Duplicate `domains[].id` values are invalid. A data product entry is an object rather than a plain string so later versions can add fields, e.g. an output port, without a breaking change.

A data product id MUST appear in at most one domain. A contract may be named by more than one domain, because a contract can bind several consumers.

### Membership and the `domain` label

ODMS is authoritative for membership: a data product exists in the mesh because a domain lists it, not because the product carries a label.

The ODCS and ODPS `domain` field remains what it is today, a free-text label. It is unchanged by this RFC. Validators SHOULD compare a resolved artifact's `domain` with the id of the domain that lists it and report a **mismatch as a warning**, never an error: the label predates ODMS, and existing artifacts will not match until their authors align them.

Membership entries reference artifacts by `id` only. Resolution is optional: a mesh document is valid without the referenced documents, and a validator that can resolve them MUST report ids it cannot resolve and ids listed in two domains.

### Governance

`governance.policies[]` declares the policies in force across the mesh. A policy is a reference to a rule written in a policy engine's own language: ODMS says where the rule is, what it is called and how to evaluate it, and defines no policy language of its own.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `governance.policies[].id` | string | yes | Unique policy key within the document. |
| `governance.policies[].appliesTo` | non-empty array | yes | Scope: `mesh`, or one or more `domains[].id`. |
| `governance.policies[].engine` | string | yes | Policy engine. `opa` is defined by this RFC; other values MAY be used. |
| `governance.policies[].url` | string | yes | Where the policy is defined and maintained. |
| `governance.policies[].package` | string | for `opa` | The Rego package the rule belongs to. |
| `governance.policies[].query` | string | for `opa` | The rule to evaluate. |

Policy scope is `mesh` or domain ids; per-property or per-contract targeting belongs to the artifact and its own policy mechanisms. Each `appliesTo` entry MUST be `mesh` or an existing `domains[].id`.

Every policy MUST be evaluable without reading the mesh's source text: `url` plus `package` and `query` locates the rule, and the evaluator supplies the document. A validator that cannot reach a policy reports it as unresolved; it MUST NOT treat an unresolved or failing policy as compliant.

#### Open Policy Agent

For `engine: opa`, the policy is a [Rego](https://www.openpolicyagent.org/docs/latest/policy-language/) module. `url` resolves to that module, `package` is its package declaration, and `query` names a rule that returns a **set of violations**:

- The evaluator passes the ODMS document as the Rego `input`.
- An empty set means the document complies with the policy.
- Each entry in a non-empty set is a violation, in the policy author's words.
- A rule that does not evaluate to a set, or that fails to evaluate, is a policy error.

Example 3 shows this end to end.

### Platform

`platform.capabilities[]` lists the self-serve capabilities the mesh offers, so a data product owner can tell what they may rely on:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `platform.capabilities[].id` | string | yes | Unique capability key. |
| `platform.capabilities[].name` | string | no | Human-readable label. |
| `platform.capabilities[].url` | string | no | Where the capability is described or consumed. |

The list is descriptive; it does not standardize what a capability does.

### Versioning

ODMS uses semantic versioning for its own `apiVersion`. Removing or renaming a field, or changing a validation rule from warning to error, is a breaking change and increments MAJOR; adding an optional field, such as a new entry field, increments MINOR.

## Alternatives

- **Keep `domain` as free text on each artifact.** Rejected: there is no inventory to validate against, ownership has nowhere to live, and spelling variants create domains silently.
- **Add a `domains` map to ODPS.** Rejected: a mesh spans products, contracts and policies from several standards; a data product also does not own the mesh it belongs to.
- **Infer the mesh from artifacts.** Rejected: ownership, policy scope and empty domains cannot be inferred from the artifacts that happen to exist.
- **Make a central catalog or registry the source of truth.** Rejected: ODMS is a portable document any tool can read, with no registry dependency. A catalog can hold it, but is not required to.
- **Resolve references inside the document.** Rejected: membership by `id` keeps the mesh readable by someone holding only part of the estate, and reuses the family's reference style.

## Decision

> The decision made by the TSC.

## Consequences

- New standard; no changes to the ODCS or ODPS schemas, and no changes to existing artifacts.
- The mesh gains a domain inventory, per-domain ownership and machine-readable policy scope.
- `domain` on ODCS and ODPS remains a label; ODMS becomes the authoritative inventory, and tooling can warn when the two disagree.
- Policies stay in the engine's language and ODMS only scopes and locates them, so an Open Policy Agent deployment can be pointed at a mesh with no translation layer.
- Organizations publish one mesh document per mesh; validators can check it without a registry.
