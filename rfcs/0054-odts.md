## Summary

Define an Open Data Taxonomy Standard (ODTS) for publishing versioned taxonomies and mappings between them. ODTS supplies the terms, hierarchy, and ranks referenced by [RFC-0053](https://github.com/bitol-io/tsc/pull/81)'s structured `classification` assignments. Organizations choose their own vocabularies.

## Motivation

A contract can record `restricted`, but a tool needs the source taxonomy to check that the term exists or compare its rank. ODTS makes these checks possible across tools. Policy documents remain the human authority, linked through `authoritativeDefinitions`.

## Design and examples

ODTS defines two document kinds: `DataTaxonomy` and `TaxonomyMapping`. The recommended file suffix is `.odts.yaml`.

### Data taxonomy

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `apiVersion` | string | Yes | ODTS format version; `v0.1.0` in this proposal. |
| `kind` | string | Yes | `DataTaxonomy`. |
| `name` | string | Yes | Machine-readable taxonomy name. |
| `version` | string | Yes | Semantic version of the taxonomy. |
| `type` | string | Yes | `flat`, `hierarchical`, or `ranked`. |
| `status` | string | Yes | `proposed`, `draft`, `active`, `deprecated`, or `retired`. |
| `description` | string | No | Scope and purpose. |
| `authoritativeDefinitions` | array | No | Links to policies, taxonomy dependencies, and other sources. |
| `provenance` | object | No | Current field attribution; see below. |
| `terms` | non-empty array | Yes | Terms in the taxonomy. |

Validators must report unsupported `apiVersion` values without interpreting the document as a supported version.

### Terms

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `term` | string | Yes | Unique term key. |
| `description` | string | No | Definition. |
| `examples` | array | No | Illustrative instances. |
| `criteria` | array | No | Conditions for applying the term. |
| `rank` | integer | For `ranked` only | Relative position; greater values outrank lower values, and ties are allowed. |
| `retired` | boolean | No | One-way retirement; retains the term for existing references. |
| `defaultSensitivity` | object | No | Expected handling assignment: `{taxonomy, term}`. |
| `regulatory` | array | No | Annotations shaped as `{regime, citation?, note?}`; `regime` is required. |
| `authoritativeDefinitions` | array | No | Sources relevant to the term. |
| `provenance` | object | No | Current field attribution. |

Keys consist of dot-separated segments matching `[a-z0-9_]+`. Matching is exact, with no trimming, case folding, or Unicode normalization. Duplicate keys are invalid.

`defaultSensitivity.taxonomy` references a root `authoritativeDefinitions` ID in the taxonomy artifact; `term` must exist in that target. Validators should warn on deviations but must not fail a contract solely for differing from the default. Regulatory annotations describe the declared relationship to a regime; policy sources provide its interpretation.

### Taxonomy types

| Type | Validation |
| --- | --- |
| `flat` | Term membership. Dots in keys have no hierarchy meaning. |
| `hierarchical` | Term membership; every dot-separated prefix must also exist as a term. |
| `ranked` | Term membership and rank aggregation. Every term requires an integer `rank`. |

Missing hierarchical prefixes and ranks on non-ranked taxonomies are invalid.

For an explicit ranked assignment on a schema object, compare its rank with assignments from the same taxonomy on its immediate properties. With complete coverage, the parent rank MUST equal the maximum child rank; tied terms satisfy the check. Nested objects participate as immediate properties and are checked separately against their own children. Assignments are never generated or inherited.

Coverage is complete when every immediate property has a structured assignment for that taxonomy. Missing fields, scalar strings, empty arrays, or arrays without that taxonomy leave coverage incomplete. Incomplete coverage or an empty property set produces an **indeterminate, non-failing diagnostic**.

### References

An RFC-0053 assignment's `taxonomy` names a root `authoritativeDefinitions.id`; its `value` matches an ODTS `terms[].term`. IDs used for references must be unique within their document, with `type: Taxonomy` and an immutable, version-specific URL resolving to exactly one `DataTaxonomy`. Missing, duplicate, unresolved, or non-taxonomy references and unknown terms are invalid. Policy-document links cannot satisfy term validation.

The URL plus the resolved artifact's `name` and `version` identifies the taxonomy version. Names and versions need not be globally unique. Local declaration IDs are aliases. ODTS uses the same reference pattern for `defaultSensitivity` and mapping endpoints.

RFC-0053 defines assignment cardinality and scope: one assignment per taxonomy per element, unordered arrays, and an empty array distinct from an absent field. Existing scalar classifications remain valid and never acquire a taxonomy by inference.

### Taxonomy mapping

A `TaxonomyMapping` publishes alignments between two taxonomy versions. It shares the `apiVersion`, `name`, `version`, `status`, `authoritativeDefinitions`, and optional `provenance` fields above, with `kind: TaxonomyMapping`. Its `authoritativeDefinitions` is required.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `from` | string | Yes | Source taxonomy declaration ID. |
| `to` | string | Yes | Target taxonomy declaration ID. |
| `mappings` | non-empty array | Yes | Alignments with the entry fields below. |
| `mappings[].sourceTerm` | string | Yes | Term key in `from`. |
| `mappings[].targetTerm` | string | Yes | Term key in `to`. |
| `mappings[].relation` | string | Yes | `exact`, `close`, `broader`, `narrower`, or `related`, following SKOS mapping semantics. |
| `mappings[].provenance` | object | No | Current field attribution. |

Both endpoint terms must exist in their referenced taxonomies. Relations describe the target relative to the source: `broader` means the target term is broader. A mapping has its own name, version, and lifecycle.

### Provenance

Artifacts, terms, and mapping entries use the [current provenance structure in RFC-0053](https://github.com/bitol-io/tsc/pull/81). Each map names immediate sibling fields, such as `provenance.description` on a term. The same attribution, author, justification, and trust rules apply.

### Versioning and lifecycle

| Change | Version increment |
| --- | --- |
| Breaking changes to terms or structure, including term removal or renaming, taxonomy type changes, and reordered ranks | MAJOR |
| Add or retire terms, insert ranks, or add annotations without changing existing term meaning | MINOR |
| Change artifact `status` | At least MINOR |
| Editorial changes without changing validation outcomes | PATCH |

Retired terms remain addressable. Validators should warn when they are cited; authoring tools should omit them from new selections. Retirement does not select a successor; a mapping may document a crosswalk.

Artifact status is immutable for each published version. Changes require a new version and do not alter older references:

- `active`: published as available; does not imply the latest version.
- `deprecated` or `retired`: existing references remain valid; validators should warn and authoring tools should avoid new references.
- `proposed` or `draft`: use as a conformance target is invalid.

Current-version discovery and mutable lifecycle notices belong to policy or catalog sources.

### Example

```yaml
apiVersion: v0.1.0
kind: DataTaxonomy
name: customer-data
version: 2.0.0
type: hierarchical
status: active
authoritativeDefinitions:
  - id: handling
    type: Taxonomy
    url: https://governance.example.com/taxonomies/handling/1.0.0.odts.yaml
  - id: customer-data-policy
    type: Policy
    url: https://governance.example.com/policies/customer-data
terms:
  - term: customer_content
    description: Data a customer provides or creates through the service.
  - term: customer_content.contact_information
    description: Data used to identify or contact a person.
    defaultSensitivity:
      taxonomy: handling
      term: restricted
    regulatory:
      - regime: GDPR
        citation: Article 4(1)
```

An ODCS contract references that version:

```yaml
authoritativeDefinitions:
  - id: customer-data
    type: Taxonomy
    url: https://governance.example.com/taxonomies/customer-data/2.0.0.odts.yaml
schema:
  - name: customers
    properties:
      - name: email
        logicalType: string
        classification:
          - taxonomy: customer-data
            value: customer_content.contact_information
```

## Alternatives

- **SKOS:** provides hierarchy and mappings; ODTS adds explicit rank, versioning, and validation rules.
- **OSDS:** describes reusable semantic definitions; ODTS defines a versioned term set.
- **Fideslang:** supplies taxonomy terms; ODTS adds an artifact envelope and declared validation semantics.
- **Bind taxonomy dimensions to contract fields:** RFC-0053 names the taxonomy within each assignment, allowing several taxonomies in one field.
- **Inline taxonomies or documentation links alone:** shared artifacts avoid duplicate definitions and supply machine-readable terms.
- **Registry IDs:** local IDs and version-specific URLs support resolution without requiring a registry.

## Consequences

- A new standard defines taxonomy and mapping artifacts for shared validation.
- RFC-0053 assignments gain resolvable term definitions while retaining scalar compatibility.
- Publishers maintain versioned artifacts alongside their governing policies.
