# Open Use Case Standard (OUCS)

Champion: Simon Harrer

Authors: Simon Harrer

Applies to:
* [ ] ODCS - Open Data Contract Standard
* [ ] ODPS - Open Data Product Standard
* [ ] OORS - Open Observability Results Standard
* [ ] OOCS - Open Orchestration and Control Standard
* [ ] OMMS - Open Maturity Model Standard
* [ ] OMDS - Open Metadata Difference Standard
* [ ] OSDS - Open Semantic Definition Standard
* [x] OUCS - Open Use Case Standard (new)

## Summary

OUCS (`kind: UseCase`) describes a business use case: what it is for, which team owns it, and which data products are built for it. Access agreements ([RFC-0056 OAAS](0056-oaas.md)) cite a use case to say why the data is needed.

## Motivation

ODPS describes data products and OAAS records who may access them. Neither says which business goal they serve. Today that lives in a demand management tool, a slide deck or the access request's free-text purpose, so you cannot ask "which data products serve this use case?" or "which access grants does this use case depend on?".

OUCS makes the use case a first-class artifact:

- Data products built for a use case are listed in it, so their value can be traced back to a business goal.
- Access agreements cite the use case, so the purpose is shared and reviewed once instead of being retyped per request.
- A use case that is managed elsewhere (e.g. a demand management tool) links there instead of copying it.

## Design and examples

An OUCS document reuses the Bitol resource header (`apiVersion`, `kind`, `id`, `name`, `status`) and extension blocks (`tags`, `authoritativeDefinitions`, `customProperties`).

### Example 1: Minimal

```yaml
apiVersion: v0.1.0
kind: UseCase
id: reduce-shelf-warmers
status: active
```

### Example 2: Structured

```yaml
apiVersion: v0.1.0
kind: UseCase
id: reduce-shelf-warmers
name: Reduce shelf warmers
status: active
team:
  name: fulfillment
description:
  purpose: Buyers stop reordering articles that have not sold for six months.
authoritativeDefinitions:
  - type: mindfuel
    url: https://app.mindfuel.ai/demands/12
  - type: businessCase
    url: https://example.com/fulfillment/clearance-playbook
customProperties:
  - property: sponsor
    value: Head of Category Management
tags:
  - retention
dataProducts:
  - id: shelf-warmers
  - id: stock-update-events
```

### Fields

| Field | Type | Required | Description |
| ----- | ---- | -------- | ----------- |
| `apiVersion` | string | yes | OUCS version. Initial version is `v0.1.0`. |
| `kind` | string | yes | Always `UseCase`. |
| `id` | string | yes | Unique identifier of the use case. |
| `name` | string | no | Human-readable label. |
| `status` | string | yes | Lifecycle state. Free text; see [Status](#status). |
| `team.name` | string | no | Id of the owning team. See [Ownership](#ownership). |
| `description.purpose` | string | no | The business outcome the use case is after. |
| `authoritativeDefinitions` | array | no | Typed links to external sources, including where the use case is managed. ODCS semantics. |
| `customProperties` | array | no | Platform-specific data, e.g. a sponsor. ODCS semantics. |
| `tags` | array of string | no | Free-form labels. |
| `dataProducts` | array | no | Data products owned by the use case. See [Data products](#data-products). |
| `dataProducts[].id` | string | yes* | Id of an ODPS data product (*required within each entry). |

### Status

`status` is free text, so organizations can use their own lifecycle. Two values have a defined meaning:

- `proposed`: the use case is not yet approved.
- `retired`: the use case has ended.

An access request (an OAAS agreement with `status: requested`) MUST NOT cite a use case whose status is `proposed` or `retired`. Any other status, e.g. `active`, can be cited.

### Ownership

`team.name` holds the id of the owning team. Without a team, the organization owners maintain the use case.

### Data products

`dataProducts` lists the data products built for the use case. The use case owns them the way a data product owns its output ports: they exist for this use case and are maintained in its context.

Entries reference a data product by `id` only for now. Each entry is an object, not a plain string, so later versions can add fields (e.g. a role or an output port) without a breaking change.

### Managed elsewhere

When a use case is managed in another tool, the OUCS document is the reference that Bitol documents point to, and `authoritativeDefinitions` links to the source, e.g. `type: mindfuel` for a demand in Mindfuel or `type: businessCase` for a business case document.

## Alternatives

- **Keep the purpose as free text in each access agreement.** Rejected: the same purpose is retyped per request, cannot be reviewed once, and does not connect data products to a business goal.
- **Add use case fields to ODPS.** Rejected: one use case spans several data products, and its lifecycle and owner differ from theirs.
- **A fixed `status` enum.** Rejected for now: organizations already run their own use case lifecycles. Only `proposed` and `retired` need a shared meaning.
- **`dataProducts` as a list of strings.** Rejected: an object can take more fields later without a breaking change.

## Decision

> The decision made by the TSC.

## Consequences

- New standard; no changes to ODCS or ODPS.
- OAAS ([RFC-0056](0056-oaas.md)) gets an optional top-level `useCaseId`.
